# 瓶颈归因唯一指向性审计（dsh-inference-tuner v0.5.0）

> 审计对象：`dsh-inference-tuner` v0.5.0 的 `lib/bottleneck.mjs` 规则表
> 方法学依据：`/zh/xiciyang/AIKB/理论基础/大模型推理性能调优分析论V2` §5.3、§7.1、§10.4
> 审计时间：2026-09-02

## TL;DR

v0.5.0 现有 8 条规则覆盖 **memory / compute / comm / scheduler / converged** 五大类。
其中 **memory + scheduler + comm 的证据唯一性基本达标**，但 **compute 类的 Decode/Prefill 区分证据不足**——DRAM 高 + SM 高 在 chunked prefill 场景下同样成立，存在误归因风险。
此外还有 **6 类方法论 §5.3 列出但插件未覆盖的瓶颈**（host、PCIe、tokenizer、activation、cache thrashing、quality regression）。

## A. 现有规则的唯一指向性逐条审计

### A.1 `ruleVramHardCap` → memory (VRAM 墙) — **PASS，唯一性达标**

证据链：`DCGM_FI_DEV_FB_USED/FB_TOTAL ≥ 0.92`。
- 唯一指向性论证：GPU 物理上没有 free VRAM 是 device 维度的硬信号；compute-bound ⇒ 算力墙 ⇒ GPU 还有空；scheduler-bound ⇒ 引擎没跑 ⇒ 没活动分配。
- 唯一已知的干扰变量：NUMA 不均衡 (CPU 节点离 GPU 远) 会让 CPU 侧的 pinned buffer 占用显现成 GPU 占用；但这不影响 "GPU 没空""的正确性。
- **唯一未补足信号**：活动分配 vs 缓存分配无法区分。碎片化导致的可分配空间不足但总量未满是一个独立墙（见 D.3）。

### A.2 `ruleKvHardCap` → memory (KV 墙) — **PASS，唯一性达标**

证据链：`vllm:gpu_cache_usage_perc ≥ 0.90` + `running > 0`，并有 preemptions / running 接近 maxRunning 的 corroborator。
- 唯一指向性论证：引擎 KV 配置容量被占满 + 仍在处理请求 ⇒ 只能通过 evict/preempt 接纳新请求。
- **潜在漏洞**：confidence 评估仅看 preemptions / running=maxRunning*0.95。如果 engine 在 evict 但没暴露 preemptions 计数（vllm 默认暴露，sglang 0.4 起暴露），规则会落到 medium confidence。可接受，但应在 evidence 里记录这个 caveat。

### A.3 `ruleSchedulerAdmission` → scheduler (准入墙) — **PASS，唯一性基本达标**

证据链：`waiting > 0` + `running/maxRunning < 0.95` + `gpuUtil < 0.85`。
- 唯一指向性论证：队列等待 + 引擎仍可接纳 + GPU 没打满 ⇒ 限制是引擎并发上限（`max_num_seqs`），不是算力。
- **潜在漏洞**：未区分"队列因客户端未送够"（输入速率墙，见 D.5）与"队列因引擎拒收"（调度墙）。两者 evidence 相同但根因不同。需补：请求到达速率（`vllm:request_success_total` 衍生率）vs 提交速率。

### A.4 `ruleComputeDecode` → compute (Decode 带宽墙) — **FAIL，唯一性不足**

证据链：`SM_UTIL ≥ 0.85` + `DRAM_USAGE ≥ 0.85` + `KV < 0.90`。
- **致命漏洞 1**：**Prefill GEMM with chunked prefill enabled 也能产生 DRAM 高 + SM 高**。
  - 场景：`--enable-chunked-prefill --chunked-prefill-size 8192`，长 prompt 拆成多个 chunk 灌进流水线，每个 chunk 都要读 weights（HBM bandwidth）+ 计算。
  - 该场景下 DRAM 高不是 Decode，是 prefill 的 "scatter-then-gather"。
  - 真正的区分指标：`vllm:time_to_first_token_seconds` histogram 高位偏胖 ⇒ Prefill 主导；`vllm:time_per_output_token_seconds` 高位偏胖 ⇒ Decode 主导。
- **致命漏洞 2**：SM_UTIL 是 SM 占用率（含 tensor cores、load/store、control），不是 tensor core 利用率。
  - 真要唯一指向：需要 `sm__pipe_tensor_op_hmma_cycles_active.avg.pct_of_peak_sustained_active`（NVIDIA ncu / nsight） 或 DCGM `DCGM_FI_PROF_SM_ACTIVE`。
- **致命漏洞 3**：MoE 模型下，expert routing 不均会导致部分 SM 闲置，看似 SM 利用率 80% 但实际是路由瓶颈（不是 DRAM）。
- **建议补**：TTFT P99 与 TPOT P99 的相对比值，作为 Decode vs Prefill 的 disambiguator。

### A.5 `ruleComputePrefill` → compute (Prefill 算力墙) — **FAIL，同上**

`SM_UTIL ≥ 0.85` + `DRAM_USAGE < 0.85` 同样被 chunked prefill 场景污染（chunked prefill 时 DRAM 中间值可能仍在阈值下）。

### A.6 `ruleComputeGeneric` → compute (无 DRAM 信号) — **N/A，降级路径**

降级而非误归因，confidence=low 并明确告知用户缺数据。OK。

### A.7 `ruleCommunicationWall` → comm (TP 不均) — **MEDIUM，唯一性不足**

证据链：`≥2 accel` + `per-card CV > 15%`。
- **漏洞 1**：per-card throughput 来自 sglang `/v1/loads` (loads[].gen_throughput)；vLLM 暴露较少。这本身就是个数据采集缺漏（见 C 节）。
- **漏洞 2**：CV 高未必是 TP 不均，也可能是输入分布偏斜（部分 rank 接到 prompt 长的请求），需要交叉证据：`num_active_tokens` per-rank 分布。
- **漏洞 3**：本规则无法区分 TP、PP、EP、DP 不均。需要 NCCL/HCCL collective 计数。
- **漏掉场景**：
  - MoE 路由不均 → expert parallel imbalance（单独的墙）
  - 流水线气泡 → PP imbalance（prefill/bubble 时间占比）

### A.8 `ruleConverged` → converged — **PASS**

无任何墙触发即为 converged。OK。

## B. 方法论 §5.3 列出但插件**未覆盖**的瓶颈

按影响频率排序：

### B.1 **Host CPU wall** — 影响频率：高（vLLM/sglang 常见瓶颈）

症状：GPU 利用率低，但请求处理慢。原因是 Python tokenization、请求调度 loop、PrefixCache hit checking 等都在 CPU。

**缺失证据**：
- `process_cpu_seconds_total` / `node_process_cpu_seconds_total`
- vLLM：`vllm:cpu_cache_usage_perc`（已有采集，但**未被任何规则消费**）
- sglang：缺少直接 host CPU metric，需要 psutil 或 nvidia-smi 的 host 侧采样

**建议规则**：`host_cpu = ruleHostCpuWall(sum)`
```js
if (sum.hostCpuUtil >= 0.85 && sum.gpuUtil < 0.50) → 'host_cpu'
```
   唯一性证据对：host CPU 高 + GPU 低 ⇒ host 在阻塞；host CPU 高 + GPU 高 ⇒ 可能是 host 准备 prompt 但 GPU 也忙。

### B.2 **PCIe / Host-to-device transfer wall** — 影响频率：中（多卡、MoE、模型权重 swap 时）

症状：GPU 利用率震荡，吞吐抖动。NVLink/PCIe 带宽饱和。

**缺失证据**：
- `DCGM_FI_DEV_PCIE_REPLAY_COUNTER`（异常重传）
- `DCGM_FI_DEV_PCIE_RX_BYTES` / `TX_BYTES`（带宽）
- `nvidia-smi -q -d UTIL` 的 PCIe 带宽
- sglang MoE：expert 权重从 CPU 节点加载到 GPU 的耗时

**建议规则**：`rulePcieBandwidthWall(sum)`
```js
if (sum.pcieBandwidthUtil >= 0.85 && sum.gpuUtil < 0.70 && sum.numAccel >= 2)
→ 'pcie'，唯一性：单卡场景不适用（PCIe 满只发生在多卡/权重加载），可与 comm wall 区分（comm 是 peer-to-peer GPU 带宽，PCIe 是 host-to-device）。
```

### B.3 **Tokenizer wall** — 影响频率：中（高 RPS、特殊字符、长 prompt）

症状：TTFT 高、TPS 低，但 GPU 利用率并不满。原因是 Python tokenization 在 CPU 单线程跑。

**缺失证据**：
- tokenizer 时长：vLLM 没有直接 tokenize metric；需要从 `vllm:request_prefill_time` 或自定义 hook
- tokenize QPS（若 tokenize 是流水的，可观测）

**建议规则**：`ruleTokenizerWall(sum)`——结合 host_cpu + TTFT 偏高的 paired evidence。

### B.4 **Activation memory wall** — 影响频率：低-中（batch 大、context 长）

症状：总 VRAM 未满，但 batch 大或 context 长时 OOM。原因是 forward pass activation 比权重还大（Bert-style 大模型 / 长 context）。

**缺失证据**：
- 当前 `gpuCacheUsage` 是 KV-cache；activation 不直接暴露。
- 间接信号：`torch.cuda.memory_reserved() / torch.cuda.max_memory_allocated()` 比例
- vLLM 0.6+ 有 `vllm:peak_activation_memory`（实验性）

**建议规则**：`ruleActivationWall(sum)`——结合 OOM event 计数 + forward pass 中 batch-size-step 增量。

### B.5 **Weight-only wall (model load)** — 影响频率：低（启动期）

症状：模型权重装不进 VRAM，启动失败或 swap。

**缺失证据**：
- 模型权重大小（配置层） vs `gpu_memory_utilization` × `memTotal`。
- `vllm:model_size`（若暴露）或启动日志。

**建议规则**：`ruleWeightWall(sum)`——只对启动期或模型 swap 事件响应。

### B.6 **Quality regression wall** — 影响频率：任意（当 lever 触发质量回退）

症状：吞吐/延迟改善，但质量退化（ΔQ > 0.5%）。

**缺失证据**：
- `deltaQ` 已在 `gateDecision` 中用作 ROLLBACK 闸门（statistics.mjs:347）。
- 但 §5.3 schema 允许 `bottleneck: "quality"`（虽然不典型），可以作为"软墙"独立归因。

**建议规则**：`ruleQualityWall(sum)`——当 `deltaQ > 0.5%` 且 throughput 不增加时。

### B.7 **Cold-start wall** — 影响频率：低（仅冷启动期）

症状：首条推理 TTFT 极高（10s+），后续恢复正常。

**缺失证据**：TTFT 的首条 vs 稳态分布。

### B.8 **Disk I/O wall (MoE)** — 影响频率：低（仅 MoE 模型）

症状：MoE expert 路由到尚未加载的 expert 时，磁盘读取阻塞。

**缺失证据**：`disk_read_bytes_total` 衍生率。

## D. 每类墙需补的具体规则

### D.1 compute wall：Decode vs Prefill 的 disambiguation

**新增证据**：
- TTFT P99 vs TPOT P99 的相对比值
  - TTFT/TPOT > 5 ⇒ Prefill-dominated
  - TTFT/TPOT < 1 ⇒ Decode-dominated

```js
function ruleComputeDecodeRefined(sum) {
  if (sum.gpuUtil == null || sum.gpuUtil < sum.config.gpuUtilComputeWall) return null
  if (sum.dramBandwidth != null && sum.dramBandwidth < sum.config.dramBandwidthWall) return null
  if (sum.kvCacheUsagePct != null && sum.kvCacheUsagePct >= sum.config.kvCacheHardCapPct) return null
  // NEW: disambiguator — if TTFT dominates, this is Prefill not Decode
  if (sum.ttftP99 != null && sum.tpotP99 != null && sum.tpotP99 > 0) {
    const ratio = sum.ttftP99 / sum.tpotP99
    if (ratio > 5) {
      // Fall through to Prefill rule
      return null
    }
  }
  return { /* ... Decode verdict with disambiguator evidence ... */ }
}
```

**新增证据字段**：在 evidence 数组中加入
```json
{"metric": "TTFT P99 / TPOT P99", "value": 0.4, "threshold": 1.0, "direction": "below", "note": "Decode-dominated"}
```

### D.2 comm wall：区分 TP / PP / EP / DP

**新增采集**：
- `num_active_tokens` per rank (sglang `loads[].num_active_tokens`)
- `prompt_tokens` per rank（如可采）

**新增规则**：
```js
function ruleExpertParallelImbalance(sum) {
  // MoE-specific: per-rank active tokens CV > threshold AND comm wall
  // already triggered ⇒ EP not TP
  if (sum.perCardActiveTokens == null || sum.perCardActiveTokens.length < 2) return null
  const cv = computeCV(sum.perCardActiveTokens)
  if (cv < 0.20) return null
  return {
    bottleneck: 'comm',
    confidence: 'high',
    rule: 'expert_parallel_imbalance',
    evidence: [
      ev('per-card active tokens CV', cv, 0.20, 'exceeds'),
      ev('note:moe', null, null, 'reference'),
    ],
    move: { parameter: 'expert_parallel_size', direction: 'review', reason: 'MoE expert routing 不均' },
  }
}
```

### D.3 memory wall：activation vs weight vs KV vs fragmentation

```js
function ruleActivationWall(sum) {
  if (sum.peakActivationMemory == null) return null
  // Forward pass: if peak activation approaches available VRAM, batch growth OOMs
  const availableVram = (sum.vramTotalMiB || 0) - (sum.vramUsedMiB || 0)
  if (sum.peakActivationMemory > availableVram * 0.8) {
    return {
      bottleneck: 'memory',
      confidence: 'high',
      rule: 'activation_memory_wall',
      evidence: [
        ev('vllm:peak_activation_memory', sum.peakActivationMemory, availableVram * 0.8, 'exceeds'),
        ev('free_vram_mib', availableVram, sum.peakActivationMemory, 'below'),
      ],
      move: { parameter: 'max_num_batched_tokens', direction: 'decrease', reason: '前向激活超可用 VRAM' },
    }
  }
  return null
}
```

### D.4 memory wall：fragmentation

```js
function ruleMemoryFragmentation(sum) {
  // nvidia-smi reports `reserved` vs `allocated`; gap = fragmentation
  if (sum.cudaReservedMiB == null || sum.cudaAllocatedMiB == null) return null
  const fragRatio = 1 - sum.cudaAllocatedMiB / sum.cudaReservedMiB
  if (fragRatio > 0.3 && sum.oomEvents > 0) {
    return { /* fragmentation verdict */ }
  }
}
```

### D.5 scheduler wall：input rate vs admission control

```js
function ruleInputRateLimited(sum) {
  // Distinguishes "client not sending" from "engine not accepting"
  if (sum.waiting == null || sum.waiting > 0) return null // admission wall has waiting
  // No waiting + low GPU + low request rate = client-side input limit
  const arrivalRate = deriveRequestArrivalRate(sum.samples) // need time series
  if (arrivalRate < 0.5 && sum.gpuUtil < 0.30) {
    return {
      bottleneck: 'scheduler',  // OR could be a separate 'input_rate' category
      confidence: 'medium',
      rule: 'input_rate_limited',
      evidence: [
        ev('request_arrival_rate', arrivalRate, 1.0, 'below'),
        ev('DCGM_FI_DEV_GPU_UTIL', sum.gpuUtil, 0.50, 'below'),
      ],
      move: { parameter: 'input_load', direction: 'increase', reason: '客户端输入不足以喂饱引擎' },
    }
  }
}
```

### D.6 host CPU wall

```js
function ruleHostCpuWall(sum) {
  if (sum.hostCpuUtil == null || sum.hostCpuUtil < 0.85) return null
  if (sum.gpuUtil != null && sum.gpuUtil >= 0.70) return null // GPU is fed, not host-limited
  return {
    bottleneck: 'host_cpu',  // NEW category
    confidence: 'high',
    rule: 'host_cpu_saturated',
    evidence: [
      ev('process_cpu_seconds_total rate', sum.hostCpuUtil, 0.85, 'exceeds'),
      ev('DCGM_FI_DEV_GPU_UTIL', sum.gpuUtil, 0.70, 'below'),
    ],
    move: { parameter: 'num_scheduler_threads', direction: 'increase', reason: 'CPU 是瓶颈' },
  }
}
```

### D.7 PCIe wall

```js
function rulePcieWall(sum) {
  if (sum.numAccel < 2 && !sum.weightLoadEvent) return null // single-card no PCIe
  if (sum.pcieBandwidthUtil < 0.85) return null
  if (sum.gpuUtil < 0.50) return null  // GPU starved by PCIe
  return {
    bottleneck: 'pcie',  // NEW category
    confidence: 'medium',
    rule: 'pcie_bandwidth_wall',
    evidence: [
      ev('DCGM_FI_DEV_PCIE_RX_BYTES util', sum.pcieBandwidthUtil, 0.85, 'exceeds'),
      ev('DCGM_FI_DEV_GPU_UTIL', sum.gpuUtil, 0.50, 'below'),
    ],
    move: { parameter: 'tensor_parallel_size', direction: 'review', reason: 'PCIe 带宽饱和' },
  }
}
```

## F. 总结

v0.5.0 的瓶颈归因覆盖了方法论 §5.3 五大基本类（memory / compute / comm / scheduler / converged），但：

1. **compute 类的 Decode/Prefill 区分唯一性不达标**（DRAM 不能区分 chunked prefill）
2. **6+ 个 §5.3 列出的瓶颈类未实现**（host / PCIe / tokenizer / activation / quality / fragmentation）
3. **comm wall 缺少细粒度区分**（TP/PP/EP/DP）
4. **数据采集不完整**（PCIe、host CPU、activation、per-rank active tokens 都缺失）

需要 v0.6.0 集中补齐 P0 + P1 项。
